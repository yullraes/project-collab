# Task 상태와 전이 규칙

- 작성일: 2026-08-24
- 최종 수정일: 2026-08-25

- 상위 정책: [도메인 정책 결정 기록](./domain-policies.md)

## 1. 문서 목적

이 문서는 프로젝트에 속한 작업의 상태, 상태별 의미와 불변식, 허용되는 전이, 전이를 수행할 수 있는 주체와 전이의 부수 효과를 정의한다.

API 경로와 HTTP 메서드는 이 문서의 범위가 아니다. 여기서 사용하는 승인, 반려, 작업 시작 등의 이름은 API가 아니라 도메인 행위를 의미한다.

문서가 충돌하면 과제 안내서를 최우선으로 해석한다. 과제 안내서가 작업 수정·삭제 권한을 가질 수 있는 주체의 범위를 정하고, 이 문서는 그 범위 안에서 Task 상태와 생명주기에 따른 수행 조건을 구체화한다.

## 2. Task와 Ticket 중 용어 선택

현재 기준 용어는 **Task(작업)** 로 정한다.

- 과제 안내서가 도메인 명칭으로 작업을 사용한다.
- 안내서의 작업은 프로젝트에 속한 할 일로 정의되어 있다.
- Ticket은 접수된 요청, 문의, 장애 또는 이슈 추적의 의미가 더 강하다.
- 승인과 반려 흐름이 있더라도 현재 명세만으로 별도의 Ticket 도메인을 도입할 근거는 부족하다.

따라서 Java 클래스와 API 자원 이름도 우선 Task를 사용한다. 도메인 맥락이 추가되어 작업이 실제로 요청 접수 단위임이 확인될 때 Ticket으로 변경할 수 있다.

## 3. 행위 주체

상태 전이 규칙에서는 다음 주체를 구분한다.

| 주체 | 의미 |
| --- | --- |
| 프로젝트 멤버 | 프로젝트의 OWNER, ADMIN, MEMBER 전체 |
| 관리자 | 프로젝트의 OWNER 또는 ADMIN |
| 생성자 | Task를 처음 등록한 사용자. 변경되지 않음 |
| 담당자 | 현재 Task를 수행하도록 지정된 사용자. 없을 수 있음 |

한 사용자가 여러 조건을 동시에 만족할 수 있다. 예를 들어 OWNER가 자신의 Task 담당자라면 관리자 권한과 담당자 권한을 모두 가진다. 생성자나 담당자 자격에 붙은 제한은 OWNER·ADMIN의 관리자 권한을 없애지 않는다. 따라서 OWNER·ADMIN은 생성자나 담당자를 겸해도 모든 상태에서 제목과 설명을 수정할 수 있다. 단, 생성자가 자신의 Task를 직접 승인할 수 없다는 명시적 금지는 예외로 우선한다.

## 4. 상태 목록

| 상태 | 의미 | 담당자 필수 여부 | 승인 내용 수정 |
| --- | --- | --- | --- |
| **PENDING** | 일반 멤버가 등록했거나, 담당자가 승인된 Task 내용을 수정해 재승인을 기다림 | 보통 있음. 생성자 멤버십 제거 시 없을 수 있음 | 생성자·관리자 가능 |
| **REJECTED** | 관리자가 반려하여 생성자의 수정을 기다림 | 보통 있음. 생성자 멤버십 제거 시 없을 수 있음 | 생성자·관리자 가능 |
| **ACCEPTED** | 승인되었지만 아직 작업을 시작하지 않음 | 선택 | 관리자 즉시 수정, 담당자 수정 시 PENDING으로 복귀 |
| **IN_PROGRESS** | 담당자가 작업을 수행 중 | 필수 | 관리자 즉시 수정, 담당자 수정 시 PENDING으로 복귀 |
| **IN_REVIEW** | 담당자가 완료 검토를 요청함 | 필수 | 관리자 즉시 수정, 담당자 수정 시 PENDING으로 복귀 |
| **DONE** | 관리자가 최종 완료를 승인함 | 선택 | 관리자 즉시 수정, 담당자 수정 시 PENDING으로 복귀 |

승인 내용은 Task의 제목과 설명을 의미한다. 관리자 권한이 없는 생성자는 ACCEPTED 이후 승인 내용을 바꿀 수 없다. 현재 담당자는 ACCEPTED 이후 승인 내용을 바꿀 수 있지만, 그 변경은 기존 승인을 무효화하여 Task를 다시 PENDING으로 되돌린다.

## 5. 전체 상태 흐름

~~~mermaid
stateDiagram-v2
    [*] --> PENDING: MEMBER 생성
    [*] --> ACCEPTED: OWNER·ADMIN 생성

    PENDING --> ACCEPTED: 관리자 승인
    PENDING --> REJECTED: 관리자 반려
    REJECTED --> PENDING: 생성자 재요청

    ACCEPTED --> IN_PROGRESS: 담당자 작업 시작
    IN_PROGRESS --> IN_REVIEW: 담당자 완료 검토 요청
    IN_REVIEW --> DONE: 관리자 완료 승인
    IN_REVIEW --> IN_PROGRESS: 관리자 보완 요청
~~~

위 그림에 없는 상태 전이는 허용하지 않는다. 담당자 해제에 따른 상태 정규화는 일반적인 상태 전이가 아니라 담당자 변경의 부수 효과이며 별도 절에서 정의한다.

## 6. Task 생성

### T-01. 일반 MEMBER의 Task 생성

- 수행자: 현재 프로젝트의 MEMBER
- 시작 상태: 없음
- 결과 상태: PENDING
- 생성자: 요청한 MEMBER
- 기본 담당자: 생성자
- 반려 사유: 없음

일반 MEMBER가 만든 Task는 즉시 실행 대상이 되지 않고 관리자 승인을 기다린다. 생성자가 담당자가 되는 것은 임의의 담당자 선택이 아니라 생성 정책에 따른 기본 배정이다.

### T-02. OWNER·ADMIN의 Task 생성

- 수행자: 현재 프로젝트의 OWNER 또는 ADMIN
- 시작 상태: 없음
- 결과 상태: ACCEPTED
- 생성자: 요청한 관리자
- 기본 담당자: 생성자
- 선택 가능한 담당자: 다른 현재 프로젝트 멤버 또는 미할당
- 반려 사유: 없음

관리자는 승인 권한을 가진 주체이므로 자신이 생성한 Task에 별도 자기 승인 단계를 적용하지 않는다.

## 7. 승인과 반려

### T-03. Task 승인

- 전이: PENDING → ACCEPTED
- 수행자: OWNER·ADMIN
- 사전 조건:
  - Task가 PENDING 상태다.
  - 수행자가 현재 프로젝트의 관리자다.
  - 생성자가 자신의 Task를 직접 승인하는 경우가 아니다.
- 담당자:
  - 별도 변경이 없으면 기존 담당자를 유지한다.
  - 관리자는 승인하면서 다른 현재 멤버에게 재할당할 수 있다.
  - 관리자는 승인하면서 담당자를 비울 수 있다.
- 부수 효과:
  - 반려 사유를 비운 상태를 유지한다.
  - 관리자 권한이 없는 생성자는 해당 자격만으로 승인 내용을 수정할 수 없게 된다.
  - 현재 담당자는 내용 수정 시 기존 승인 상태를 유지하지 못하고 다시 PENDING으로 되돌아간다.

### T-04. Task 반려

- 전이: PENDING → REJECTED
- 수행자: OWNER·ADMIN
- 사전 조건:
  - Task가 PENDING 상태다.
  - 수행자가 현재 프로젝트의 관리자다.
  - 짧은 반려 사유가 제공된다.
- 부수 효과:
  - 최신 반려 사유를 Task에 저장한다.
  - Task와 담당자는 삭제하거나 자동 변경하지 않는다.
  - 프로젝트 멤버 전원에게 계속 노출한다.

### T-05. Task 재요청

- 전이: REJECTED → PENDING
- 수행자: Task 생성자
- 사전 조건:
  - Task가 REJECTED 상태다.
  - 수행자가 Task 생성자이며 현재 프로젝트 멤버다.
- 부수 효과:
  - 기존 반려 사유를 비운다.
  - 생성자와 담당자는 변경하지 않는다.

내용 수정과 재요청은 서로 다른 행위다. REJECTED Task의 제목이나 설명을 수정하는 것만으로 상태가 PENDING으로 바뀌지 않는다.

## 8. 실행과 완료

### T-06. 작업 시작

- 전이: ACCEPTED → IN_PROGRESS
- 수행자: 현재 담당자
- 사전 조건:
  - Task가 ACCEPTED 상태다.
  - 담당자가 지정되어 있다.
  - 수행자가 현재 담당자다.
  - 담당자가 현재 프로젝트 멤버다.
- 부수 효과: 없음

관리자는 담당자가 아니라면 Task를 대신 시작할 수 없다. 관리자가 담당자로 지정된 경우에는 담당자 자격으로 시작할 수 있다.

### T-07. 완료 검토 요청

- 전이: IN_PROGRESS → IN_REVIEW
- 수행자: 현재 담당자
- 사전 조건:
  - Task가 IN_PROGRESS 상태다.
  - 수행자가 현재 담당자다.
  - 담당자가 현재 프로젝트 멤버다.
- 부수 효과: 없음

담당자는 Task를 직접 DONE으로 만들 수 없다.

### T-08. 완료 승인

- 전이: IN_REVIEW → DONE
- 수행자: OWNER·ADMIN
- 사전 조건:
  - Task가 IN_REVIEW 상태다.
  - 수행자가 현재 프로젝트의 관리자다.
- 부수 효과: 없음

DONE은 담당자의 완료 선언이 아니라 관리자의 최종 완료 판정이다.

### T-09. 보완 요청

- 전이: IN_REVIEW → IN_PROGRESS
- 수행자: OWNER·ADMIN
- 사전 조건:
  - Task가 IN_REVIEW 상태다.
  - 수행자가 현재 프로젝트의 관리자다.
  - 현재 담당자가 존재한다.
- 부수 효과: 없음

별도의 보완 요청 이력이나 댓글 모델은 현재 정책에 포함하지 않는다.

## 9. 상태를 바꾸지 않는 내용 수정

### C-01. 생성자의 승인 전 내용 수정

- 대상 상태: PENDING, REJECTED
- 수행자: Task 생성자
- 수정 가능 항목: 제목, 설명
- 수정 불가 항목: 생성자, 담당자, 승인 결과, 실행 상태
- 상태 변화: 없음

REJECTED 상태에서 수정한 뒤에는 T-05 재요청을 별도로 수행해야 한다.

### C-02. 관리자의 내용 수정

- 대상 상태: 모든 상태
- 수행자: OWNER·ADMIN
- 수정 가능 항목: 제목, 설명
- 상태 변화: 없음

OWNER·ADMIN이 생성자나 담당자를 겸하더라도 관리자 권한으로 제목과 설명을 수정할 수 있다. ACCEPTED 이후 관리자가 제목이나 설명을 변경하면 관리자 권한에 의한 즉시 승인으로 간주하고 기존 상태를 유지한다.

### C-03. 담당자의 수정 범위

- 현재 담당자는 ACCEPTED, IN_PROGRESS, IN_REVIEW, DONE 상태에서 제목과 설명을 수정할 수 있다.
- 현재 담당자가 승인된 Task의 제목이나 설명을 수정하면 상태를 PENDING으로 되돌리고 기존 반려 사유는 비운다.
- 이때 담당자는 유지한다. 따라서 재승인 전 PENDING 상태에서도 생성자와 담당자가 다를 수 있다.
- 현재 담당자가 아닌 생성자는 ACCEPTED 이후 제목과 설명을 수정할 수 없다.
- 담당자 자격만으로는 자신에게 허용되지 않은 상태로 직접 변경할 수 없다.
- 담당자가 OWNER·ADMIN도 겸한다면 C-02와 관리자 상태 전이 규칙을 관리자 자격으로 수행할 수 있다.

## 10. 담당자 관리

### A-01. 담당자 지정·재할당

- 수행자: OWNER·ADMIN
- 대상: ACCEPTED, IN_PROGRESS, IN_REVIEW, DONE 상태의 Task
- 새 담당자: 현재 프로젝트 멤버만 가능
- 상태 변화: 없음

담당자를 지정하는 것만으로 ACCEPTED Task가 IN_PROGRESS로 바뀌지는 않는다. 새 담당자가 직접 작업을 시작해야 한다.

PENDING의 담당자 변경은 승인과 함께 수행하며, REJECTED에서는 담당자를 변경하지 않는다. 두 상태 모두 생성자의 멤버십 제거로 담당자가 비는 경우만 예외다.

### A-02. 관리자의 담당자 해제

- 수행자: OWNER·ADMIN
- 대상: ACCEPTED, IN_PROGRESS, IN_REVIEW, DONE 상태의 Task
- 부수 효과:
  - 담당자를 비운다.
  - 기존 상태에 따라 상태 정규화 규칙을 적용한다.

### A-03. 담당자의 자발적 포기

- 수행자: 현재 담당자
- 대상: ACCEPTED, IN_PROGRESS, IN_REVIEW, DONE 상태의 Task
- 제한:
  - 다른 사용자를 새 담당자로 지정할 수 없다.
  - 자신의 담당만 해제할 수 있다.
- 부수 효과:
  - 담당자를 비운다.
  - 기존 상태에 따라 상태 정규화 규칙을 적용한다.

### A-04. 프로젝트 멤버 제거

- 수행자: 멤버 제거 권한을 가진 관리자 또는 본인의 탈퇴
- 부수 효과:
  - 제거되는 멤버가 담당하던 모든 Task를 미할당으로 변경한다.
  - 각 Task에 상태 정규화 규칙을 적용한다.
  - Task 생성자 정보는 유지한다.
  - 멤버 제거 결과에 변경된 Task 수를 포함하지 않는다.

## 11. 담당자 해제 시 상태 정규화

담당자 해제 원인이 관리자 변경, 담당자의 자발적 포기, 프로젝트 멤버 제거 중 무엇이든 같은 규칙을 적용한다.

| 기존 상태 | 새 상태 | 설명 |
| --- | --- | --- |
| PENDING | PENDING | 승인 대기는 담당자 없이 가능 |
| REJECTED | REJECTED | 반려 상태는 담당 여부와 무관 |
| ACCEPTED | ACCEPTED | 승인된 미할당 Task로 유지 |
| IN_PROGRESS | ACCEPTED | 수행자가 없으므로 진행 중 상태를 종료 |
| IN_REVIEW | ACCEPTED | 검토 중이던 실행 흐름을 종료하고 재배정 대기로 복귀 |
| DONE | DONE | 완료 사실은 담당자 해제로 바뀌지 않음 |

IN_PROGRESS와 IN_REVIEW는 담당자가 반드시 존재해야 한다. 담당자가 사라지는 같은 트랜잭션 안에서 ACCEPTED로 되돌려 담당자 없는 활성 Task가 저장되지 않도록 한다.

## 12. 삭제

삭제는 상태 전이가 아니라 Task 자체를 제거하는 행위다.

과제 안내서의 `담당자 본인 또는 OWNER·ADMIN`은 삭제 권한을 가질 수 있는 주체의 범위다. 아래 표는 그 범위 안에서 승인 전 제안과 승인된 프로젝트 Task의 생명주기를 구분하여 상태별 삭제 조건을 구체화한다.

| 현재 상태 | 삭제 가능 주체 | 결과 |
| --- | --- | --- |
| PENDING | 현재 담당자(생성자) 또는 OWNER·ADMIN | 완전 삭제 |
| REJECTED | 현재 담당자(생성자) 또는 OWNER·ADMIN | 완전 삭제 |
| ACCEPTED | OWNER·ADMIN | 완전 삭제 |
| IN_PROGRESS | OWNER·ADMIN | 완전 삭제 |
| IN_REVIEW | OWNER·ADMIN | 완전 삭제 |
| DONE | OWNER·ADMIN | 완전 삭제 |

- PENDING과 REJECTED의 생성자는 자신의 제안을 철회하는 의미로 Task를 삭제할 수 있다.
- 생성자가 프로젝트에서 제거되어 담당자가 없다면 해당 Task는 OWNER·ADMIN만 삭제할 수 있다.
- ACCEPTED 이후 Task의 생명주기는 프로젝트 관리자가 관리한다.
- ACCEPTED 이후 관리자 권한이 없는 담당자가 Task를 수행할 수 없다고 판단하면 삭제가 아니라 담당 포기를 수행한다.
- OWNER·ADMIN이 담당자를 겸한다면 관리자 자격으로 상태와 관계없이 Task를 삭제할 수 있다.
- DONE 상태가 되어도 자동으로 삭제하지 않는다.
- 삭제 이력, 휴지통, 복구, 소프트 삭제는 구현하지 않는다.
- 이전의 `담당자는 DONE에서만 삭제할 수 있다`는 결정은 폐기했으며, 변경 이력은 상위 문서의 10.2절에 보존한다.

## 13. 상태별 불변식

### 모든 상태

- 생성자는 항상 존재하며 변경되지 않는다.
- 담당자가 존재한다면 현재 프로젝트 멤버여야 한다.
- 프로젝트 외부 사용자는 Task를 조회하거나 변경할 수 없다.
- 제목과 설명은 현재 입력 검증 정책을 만족해야 한다.

### PENDING

- 반려 사유가 없다.
- MEMBER가 처음 만든 PENDING Task에서는 생성자와 담당자가 같다.
- 승인된 Task의 내용을 담당자가 수정해 재승인을 요청한 PENDING Task에서는 생성자와 담당자가 다를 수 있다.
- 생성자가 프로젝트에서 제거된 경우에는 담당자가 없을 수 있다.
- 생성자 또는 관리자가 승인 내용을 수정할 수 있다.
- 관리자만 승인하거나 반려할 수 있다.

### REJECTED

- 최신 반려 사유가 존재한다.
- 반려 직전 담당자를 유지한다.
- 생성자가 프로젝트에서 제거된 경우에만 담당자가 없을 수 있다.
- 생성자 또는 관리자가 승인 내용을 수정할 수 있다.
- 생성자만 재요청할 수 있다.

### ACCEPTED

- 반려 사유가 없다.
- 담당자가 없어도 존재할 수 있다.
- 담당자가 있는 경우에만 작업을 시작할 수 있다.
- 현재 담당자는 승인 내용을 수정할 수 있지만 수정 결과는 PENDING이다. OWNER·ADMIN을 겸하면 관리자 자격으로 상태를 유지한 채 수정할 수 있다.

### IN_PROGRESS

- 담당자가 반드시 존재한다.
- 현재 담당자만 완료 검토를 요청할 수 있다.
- 현재 담당자는 승인 내용을 수정할 수 있지만 수정 결과는 PENDING이다. OWNER·ADMIN을 겸하면 관리자 자격으로 상태를 유지한 채 수정할 수 있다.

### IN_REVIEW

- 담당자가 반드시 존재한다.
- 관리자만 완료하거나 IN_PROGRESS로 되돌릴 수 있다.
- 현재 담당자는 승인 내용을 수정할 수 있지만 수정 결과는 PENDING이다. OWNER·ADMIN을 겸하면 관리자 자격으로 상태를 유지한 채 수정할 수 있다.

### DONE

- 종료 상태이며 다른 상태로 되돌리지 않는다.
- 담당자는 멤버 제거 또는 담당 포기로 인해 없을 수 있다.
- 자동 삭제하지 않는다.

## 14. 허용하지 않는 전이 예시

다음 전이는 현재 정책에서 허용하지 않는다.

- PENDING → IN_PROGRESS
- PENDING → DONE
- REJECTED → ACCEPTED
- REJECTED → IN_PROGRESS
- ACCEPTED → DONE
- ACCEPTED → IN_REVIEW
- ACCEPTED → ACCEPTED
  - 단, 담당자의 내용 수정은 PENDING으로 되돌리는 예외다.
- IN_PROGRESS → ACCEPTED
  - 단, 담당자 해제에 따른 상태 정규화는 예외다.
- IN_PROGRESS → IN_PROGRESS
  - 단, 담당자의 내용 수정은 PENDING으로 되돌리는 예외다.
- IN_PROGRESS → DONE
- IN_REVIEW → ACCEPTED
  - 단, 담당자 해제에 따른 상태 정규화는 예외다.
- IN_REVIEW → IN_REVIEW
  - 단, 담당자의 내용 수정은 PENDING으로 되돌리는 예외다.
- DONE → IN_PROGRESS
- DONE → ACCEPTED

전이 명령을 반복 호출했을 때 현재 상태가 요구되는 시작 상태와 다르면 유효한 전이로 처리하지 않는다.

## 15. 대표 시나리오

### 15.1 일반 멤버가 제안한 작업의 정상 완료

~~~text
MEMBER가 Task 생성
→ PENDING, 생성자=담당자
→ 관리자가 승인
→ ACCEPTED, 담당자 유지
→ 담당자가 작업 시작
→ IN_PROGRESS
→ 담당자가 완료 검토 요청
→ IN_REVIEW
→ 관리자가 완료 승인
→ DONE
~~~

### 15.2 반려 후 재요청

~~~text
MEMBER가 Task 생성
→ PENDING
→ 관리자가 반려 사유와 함께 반려
→ REJECTED
→ 생성자가 제목·설명 수정
→ REJECTED 유지
→ 생성자가 재요청
→ PENDING, 반려 사유 제거
→ 관리자가 승인
→ ACCEPTED
~~~

### 15.3 진행 중 담당 포기

~~~text
ACCEPTED
→ 담당자가 작업 시작
→ IN_PROGRESS
→ 담당자가 담당 포기
→ 담당자 없음, ACCEPTED
→ 관리자가 새 담당자 지정
→ ACCEPTED
→ 새 담당자가 작업 시작
→ IN_PROGRESS
~~~

### 15.4 검토 중 담당자 멤버십 제거

~~~text
IN_REVIEW
→ 관리자가 현재 담당자를 프로젝트에서 제거
→ 담당자 없음, ACCEPTED
→ Task 생성자 정보는 유지
~~~

## 16. 동시성 규칙

- Task는 낙관적 동시성 제어 대상이다.
- 조회 결과에는 Task의 현재 리비전을 포함한다.
- 이 문서에 정의된 Task 변경 명령은 조회 당시 리비전을 함께 전달한다.
- 현재 리비전과 요청 리비전이 다르면 변경을 적용하지 않는다.
- 충돌 시 자동 병합하거나 마지막 요청으로 덮어쓰지 않고 최신 Task를 다시 조회하도록 한다.
- 관리자 여러 명의 승인·반려 또는 완료·보완 요청 중 먼저 유효하게 반영된 한 요청만 성공한다.
- 생성자의 내용 수정과 관리자의 승인·반려가 충돌하면 한 요청만 성공한다.
- 담당자 변경과 상태 전환이 충돌해도 한 요청만 성공한다.
- 상태가 요구되는 시작 상태와 다르면 잘못된 상태 전이이며, 리비전 불일치와 구분한다.
- JPA 영속 엔티티에서는 **@Version**을 기본 구현 수단으로 사용할 수 있다.
- 도메인 엔티티와 애플리케이션 명령에는 JPA 엔티티 대신 리비전 값을 전달한다.
- JPQL 또는 SQL 벌크 갱신에서는 버전 조건과 버전 증가를 직접 적용한다.

## 17. 아직 결정하지 않은 항목

- 리비전을 요청 본문으로 받을지 HTTP 조건부 요청 헤더로 받을지
- 충돌과 잘못된 상태 전이를 어떤 HTTP 상태와 오류 코드로 표현할지
- 반려 사유와 제목·설명의 구체적인 최대 길이
- 생성자가 프로젝트에서 제거된 REJECTED Task의 후속 처리

담당자 지정과 프로젝트 멤버 제거의 교차 동시성, 여러 Task 정규화의 리비전 처리 방식은 [트랜잭션 경계 설계 4.2절과 4.3절](./transaction-boundaries.md#42-담당자-지정과-멤버-제거의-경쟁)을 따른다.
