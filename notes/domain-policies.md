# Project Collab 도메인 정책 결정 기록

- 작성일: 2026-08-24
- 최종 수정일: 2026-08-25
- 상태: 도메인 정책 초안
- 근거: 과제 안내서와 과제 메일, 정책 논의 내용

## 1. 문서 목적

이 문서는 과제 명세에 직접 적힌 규칙과, 명세가 비워 둔 부분에 대해 선택한 도메인 정책을 구분하여 기록한다.

정책을 정할 때는 다음 원칙을 사용한다.

1. 과제 명세에 명시된 권한과 기능을 위반하지 않는다.
2. 새로운 제품 범위나 업무 도메인을 불필요하게 상상하지 않는다.
3. 주어진 사용자·프로젝트·멤버·작업이 모순 없이 동작하는 데 필요한 정책만 추가한다.
4. 구현과 설명이 복잡해지는 기능은 현재 과제 범위에서 제외한다.

문서 간 해석 기준은 다음과 같다.

1. 과제 안내서를 최상위 기준으로 사용한다.
2. 멤버·역할 영역에서 과제 안내서가 비워 둔 상세 정책은 [프로젝트 멤버·역할 사용자 시나리오](./user-scenarios/02-project-members.md)를 최신 기준으로 사용한다.
3. 이 문서와 세부 정책 문서는 위 두 기준에 맞춰 해석한다.

이 문서는 API 경로, 요청·응답 DTO, HTTP 상태 코드 같은 API 명세를 확정하기 위한 문서가 아니다. API 시나리오는 도메인 정책 확정 후 별도로 작성한다.

## 2. 과제 명세에서 고정된 규칙

다음 규칙은 선택 사항이 아니라 과제 명세에서 직접 제시된 내용이다.

- 역할은 **OWNER**, **ADMIN**, **MEMBER** 세 가지다.
- 인증은 과제 구현 범위 밖으로 두며, 요청자의 식별자는 API 파라미터로 전달된다고 가정한다.
- 프로젝트 생성자는 해당 프로젝트의 OWNER가 된다.
- 프로젝트 삭제는 OWNER만 가능하다.
- 프로젝트 수정은 OWNER와 ADMIN이 가능하다.
- 멤버 추가·역할 변경·제거는 OWNER와 ADMIN이 수행한다.
- 프로젝트 상세와 멤버 목록은 프로젝트 멤버 전원이 조회할 수 있다.
- 작업 생성·조회·목록 조회는 프로젝트 멤버 전원이 수행할 수 있다.
- 작업 수정·삭제 권한의 주체는 담당자 본인 또는 OWNER·ADMIN이다.
- 프로젝트에는 항상 최소 한 명의 OWNER가 있어야 한다.
- 프로젝트 외부 사용자는 해당 프로젝트와 작업에 접근할 수 없다.
- 작업 상태 종류와 그 밖의 속성은 지원자가 결정한다.
- 동시 수정 시 앞선 변경이 덮어써지는 상황의 처리 방식은 지원자가 결정한다.

명세의 권한표는 각 행위를 수행할 수 있는 상위 주체를 정한다. 아래 정책은 그 주체 범위 안에서 역할 대상과 작업 상태에 따른 조건을 구체화한다. ADMIN의 다른 ADMIN 관리 제한과 Task 상태별 수정·삭제 제한도 이러한 상세 조건이며, 명세에 없는 주체에게 새 권한을 부여하지 않는다.

## 3. 용어

- **관리자**: OWNER와 ADMIN을 함께 지칭한다.
- **생성자**: 작업을 처음 등록한 프로젝트 멤버다. 생성 후 변경되지 않는다.
- **담당자**: 현재 작업을 수행하는 프로젝트 멤버다. 지정하지 않을 수 있으며 변경될 수 있다.
- **승인 내용**: 작업의 제목과 설명을 의미한다.
- **실행 상태**: 승인 후 실제 작업의 진행 상태를 의미한다.

## 4. 프로젝트 소유권과 역할

### 4.1 OWNER와 ADMIN의 의미

- 프로젝트에는 정확히 한 명의 OWNER만 존재한다.
- OWNER는 프로젝트의 존속과 소유권에 대한 최종 책임자다.
- ADMIN은 프로젝트 내부의 일상적인 운영 관리자다.
- OWNER는 ADMIN이 할 수 있는 운영 작업도 모두 수행할 수 있다.

### 4.2 멤버 추가와 역할 관리 범위

- 서비스에 등록된 사용자만 프로젝트 멤버로 추가할 수 있다.
- 새로 추가한 멤버의 초기 역할은 MEMBER다.
- 이미 같은 프로젝트의 현재 멤버인 사용자를 다시 추가하면 거부하고 기존 멤버십과 역할을 유지한다.

| 작업 | OWNER | ADMIN |
| --- | --- | --- |
| MEMBER 추가·제거 | 가능 | 가능 |
| MEMBER를 ADMIN으로 승격 | 가능 | 가능 |
| 기존 ADMIN 강등·제거 | 가능 | 불가 |
| 다른 ADMIN의 멤버십 변경 | 가능 | 불가 |
| 프로젝트 수정 | 가능 | 가능 |
| 프로젝트 삭제 | 가능 | 불가 |
| 소유권 이전 | 가능 | 불가 |

- ADMIN은 MEMBER를 ADMIN으로 승격할 수 있다.
- ADMIN은 이미 ADMIN인 다른 사용자의 역할이나 멤버십을 변경할 수 없다.
- ADMIN은 스스로 MEMBER로 강등하거나 프로젝트에서 탈퇴할 수 있다.
- MEMBER는 스스로 프로젝트에서 탈퇴할 수 있다.
- OWNER는 소유권을 이전하기 전에는 강등하거나 탈퇴할 수 없다.

### 4.3 소유권 이전

- 소유권 이전 대상은 현재 프로젝트의 ADMIN이어야 한다.
- 이전은 하나의 트랜잭션에서 원자적으로 수행한다.
- 기존 OWNER는 ADMIN이 된다.
- 이전 대상 ADMIN은 OWNER가 된다.
- 이전 과정에서 OWNER가 0명 또는 2명인 상태를 저장하지 않는다.
- 별도의 OWNER 후보 역할이나 후보 지정 기능은 구현하지 않는다.
- 계정 분실·장기 부재에 대한 운영자 복구 절차는 현재 과제 범위 밖이다.

### 4.4 프로젝트 삭제

- 현재 OWNER만 프로젝트를 삭제할 수 있다.
- 작업이 남아 있어도 프로젝트 삭제를 허용한다.
- 프로젝트 삭제 시 프로젝트, 멤버십, 소속 작업을 모두 완전 삭제한다.
- 사용자 계정은 프로젝트 외부 자원이므로 삭제하지 않는다.
- 휴지통, 복구, 소프트 삭제는 구현하지 않는다.

## 5. 작업 생성과 승인

### 5.1 생성

- 프로젝트 멤버 전원은 작업을 생성할 수 있다.
- 일반 MEMBER가 생성한 작업은 **PENDING** 상태가 된다.
- 생성자가 최초 담당자로 자동 지정된다.
- **PENDING**과 **REJECTED**에서는 기존 담당자를 유지한다.
- MEMBER가 처음 생성한 **PENDING** Task는 생성자를 담당자로 시작한다.
- 관리자가 승인된 Task를 다시 승인 대기로 되돌리지 않는 한, 관리자는 **PENDING**과 **REJECTED**에서 담당자를 별도로 재할당하거나 미할당으로 바꾸지 않는다.
- 단, 생성자가 프로젝트에서 제거되면 멤버 제거 정책에 따라 담당자만 비운다.
- OWNER·ADMIN이 직접 생성한 작업은 별도 승인 없이 **ACCEPTED** 상태가 된다.
- OWNER·ADMIN이 작업을 생성할 때도 생성자를 기본 담당자로 사용한다.
- OWNER·ADMIN은 생성 시 다른 현재 멤버를 담당자로 지정하거나 미할당으로 생성할 수 있다.
- 생성자가 담당자가 되는 것은 사용자가 임의의 담당자를 선택하는 행위가 아니라 생성 정책에 따른 기본 배정이다.

### 5.2 승인과 반려

- **PENDING → ACCEPTED** 전환은 OWNER·ADMIN만 수행한다.
- 승인 시 별도 담당자 변경이 없으면 생성자를 담당자로 유지한다.
- 승인하면서 다른 현재 멤버에게 재할당하거나 미할당 상태로 바꿀 수 있다.
- **PENDING → REJECTED** 전환은 OWNER·ADMIN만 수행한다.
- REJECTED 작업은 삭제하지 않고 프로젝트 멤버에게 계속 노출한다.
- 생성자는 REJECTED 작업의 제목과 설명을 수정한 뒤 다시 요청할 수 있다.
- 재요청은 **REJECTED → PENDING** 전환이다.
- 생성자는 자신의 작업을 직접 승인할 수 없다.

### 5.3 반려 사유

- 반려 시 짧은 반려 사유 하나를 저장한다.
- 별도의 리뷰 엔티티, 댓글, 반려 이력은 만들지 않는다.
- 최신 반려 사유만 유지한다.
- 재요청하면 기존 반려 사유를 비운다.
- 다시 반려되면 새 사유로 덮어쓴다.

## 6. 생성자와 담당자

### 6.1 생성자

- 생성자는 작업 생성 시 결정하며 변경하지 않는다.
- 생성자와 담당자는 서로 다른 속성으로 저장한다.
- 담당자가 바뀌거나 미할당이 되어도 생성자 정보는 유지한다.
- REJECTED 작업의 수정과 재요청 권한은 생성자를 기준으로 판단한다.

### 6.2 담당자

- 작업은 담당자 없이 존재할 수 있다.
- 담당자를 지정한다면 반드시 해당 프로젝트의 현재 멤버여야 한다.
- 프로젝트 멤버 전원은 모든 작업을 조회할 수 있지만, 조회 권한만으로 담당자가 되지는 않는다.
- OWNER·ADMIN은 승인하면서 또는 **ACCEPTED** 이후 담당자를 지정·변경·해제할 수 있다.
- MEMBER가 처음 생성한 **PENDING** Task에서는 생성자가 담당자다.
- 승인된 Task를 현재 담당자가 수정해 재승인 대기로 되돌린 경우, **PENDING**에서도 담당자와 생성자가 다를 수 있다.
- **REJECTED**에서는 반려 직전의 담당자를 유지한다. 생성자 멤버십 제거에 따른 미할당만 예외다.
- 담당자는 다른 사람을 담당자로 지정할 수 없다.
- 담당자는 **ACCEPTED** 이후 자신의 담당을 포기할 수 있다.

### 6.3 멤버 제거

- 멤버 제거 시 해당 멤버가 담당하던 작업은 미할당으로 변경한다.
- 작업 생성자 정보는 유지한다.
- 멤버 제거 응답에는 미할당으로 변경된 작업 수를 포함하지 않는다.

## 7. 작업 상태

### 7.1 상태 목록

- **PENDING**: 일반 멤버가 등록하여 관리자 승인을 기다리는 상태
- **REJECTED**: 관리자가 반려하여 생성자의 수정을 기다리는 상태
- **ACCEPTED**: 승인되었지만 작업을 시작하지 않은 상태
- **IN_PROGRESS**: 담당자가 작업을 수행 중인 상태
- **IN_REVIEW**: 담당자가 작업 완료 검토를 요청한 상태
- **DONE**: 관리자가 최종 완료를 승인한 상태

### 7.2 상태 흐름

~~~text
PENDING ──관리자 승인──> ACCEPTED
   │
   └──관리자 반려──> REJECTED ──생성자 재요청──> PENDING

ACCEPTED ──담당자 시작──> IN_PROGRESS
IN_PROGRESS ──담당자 검토 요청──> IN_REVIEW
IN_REVIEW ──관리자 완료 승인──> DONE
IN_REVIEW ──관리자 보완 요청──> IN_PROGRESS
~~~

- 담당자가 지정된 작업만 **ACCEPTED → IN_PROGRESS**로 전환할 수 있다.
- **ACCEPTED → IN_PROGRESS** 전환은 현재 담당자만 수행한다.
- **IN_PROGRESS → IN_REVIEW** 전환은 현재 담당자만 수행한다.
- **IN_REVIEW → DONE** 전환은 OWNER·ADMIN만 수행한다.
- 완료로 보기 어려운 경우 OWNER·ADMIN은 **IN_REVIEW → IN_PROGRESS**로 되돌린다.
- 위에서 정의하지 않은 역방향 전환이나 재개 기능은 구현하지 않는다.

## 8. 작업 내용 수정

- 한 사용자가 여러 자격을 함께 가지면 현재 행위에 권한이 있는 자격을 기준으로 판단한다.
- OWNER·ADMIN이 해당 Task의 생성자나 담당자이기도 한 경우에는 관리자 권한이 적용되므로 모든 상태에서 제목과 설명을 수정할 수 있다.
- PENDING 상태에서는 생성자가 제목과 설명을 수정할 수 있다.
- REJECTED 상태에서는 생성자가 제목과 설명을 수정할 수 있다.
- REJECTED 작업의 내용 수정만으로 재요청되지는 않는다. 재요청 전환을 별도로 수행한다.
- ACCEPTED, IN_PROGRESS, IN_REVIEW, DONE 상태에서는 현재 담당자가 제목과 설명을 수정할 수 있다.
- 관리자가 아닌 담당자가 승인된 Task를 수정하면 상태를 **PENDING**으로 되돌려 다시 승인을 받아야 한다.
- 승인된 Task에서 현재 담당자가 아닌 생성자는 제목과 설명을 수정할 수 없다.
- OWNER·ADMIN은 모든 상태에서 제목과 설명을 수정할 수 있다.
- 관리자가 승인 후 제목이나 설명을 수정하면 관리자의 즉시 승인으로 보고 기존 상태를 유지한다.

## 9. 담당자 해제 시 상태 정리

담당자가 자발적으로 담당을 포기하거나 멤버 제거로 담당자가 해제되는 경우 같은 규칙을 적용한다.

| 기존 상태 | 담당자 해제 후 상태 |
| --- | --- |
| PENDING | PENDING |
| REJECTED | REJECTED |
| ACCEPTED | ACCEPTED |
| IN_PROGRESS | ACCEPTED |
| IN_REVIEW | ACCEPTED |
| DONE | DONE |

- IN_PROGRESS와 IN_REVIEW는 담당자 없는 활성 상태로 유지하지 않는다.
- 담당자가 해제되면 위 두 상태만 ACCEPTED로 되돌린다.
- DONE의 완료 사실은 담당자 해제로 변경하지 않는다.

## 10. 작업 삭제

### 10.1 현재 정책

- DONE 작업은 자동 삭제하지 않고 계속 보존한다.
- 작업은 명시적인 삭제 요청이 있을 때만 완전 삭제한다.
- 휴지통, 복구, 삭제 이력은 구현하지 않는다.
- 아래 상태별 삭제 정책은 과제 안내서가 허용한 담당자와 OWNER·ADMIN의 범위 안에서 삭제 조건을 구체화한 것이다.

| 작업 상태 | 삭제 가능 주체 |
| --- | --- |
| PENDING | 현재 담당자(생성자), OWNER·ADMIN |
| REJECTED | 현재 담당자(생성자), OWNER·ADMIN |
| ACCEPTED | OWNER·ADMIN |
| IN_PROGRESS | OWNER·ADMIN |
| IN_REVIEW | OWNER·ADMIN |
| DONE | OWNER·ADMIN |

- PENDING과 REJECTED에서는 생성자와 담당자가 같으므로, 생성자는 자신의 제안을 철회한다는 의미로 Task를 삭제할 수 있다.
- 생성자가 프로젝트에서 제거되어 담당자가 없다면 OWNER·ADMIN만 삭제할 수 있다.
- ACCEPTED가 된 Task는 개인의 제안이 아니라 프로젝트가 승인한 작업으로 본다.
- ACCEPTED 이후 관리자 자격이 없는 담당자는 Task 자체를 삭제할 수 없으며, 수행할 수 없다고 판단하면 자신의 담당을 포기한다.
- 담당 포기로 미할당된 Task는 OWNER·ADMIN이 재할당하거나 삭제한다.
- DONE Task도 기본적으로 보존하며, 예외적인 완전 삭제는 OWNER·ADMIN이 결정한다.

### 10.2 결정 변경 이력

- 초기 결정은 담당자가 DONE 상태에서만 Task를 삭제할 수 있고, 다른 상태에서는 OWNER·ADMIN만 삭제할 수 있다는 것이었다.
- 이 결정은 담당자에게 명세상 삭제 권한을 주면서도 진행 중 Task의 삭제를 관리자가 통제하려는 취지였다.
- 이후 승인 전에는 생성자가 제안을 소유하지만 ACCEPTED 이후에는 프로젝트가 Task의 생명주기를 관리한다는 기준으로 정책을 변경했다.
- 이에 따라 초기 결정은 더 이상 적용하지 않으며, 현재는 생성자와 담당자가 같은 PENDING·REJECTED에서만 담당자 삭제를 허용한다.

## 12. 동시 수정

- Task 변경에는 낙관적 동시성 제어를 적용한다.
- Task 조회 결과에는 현재 리비전을 포함한다.
- Task를 직접 변경하는 명령은 사용자가 조회한 리비전을 함께 전달한다.
- 현재 리비전과 요청 리비전이 다르면 변경을 거절하고 최신 Task를 다시 조회하도록 한다.
- 마지막 요청 우선과 자동 병합은 사용하지 않는다.
- 승인·반려·내용 수정·상태 전환·담당자 변경·담당 포기·삭제에 같은 원칙을 적용한다.
- JPA 영속 엔티티에서는 **@Version**을 기본 구현 수단으로 사용할 수 있다.
- 도메인 계층에는 JPA 엔티티를 노출하지 않고 리비전을 동시성 토큰으로 전달한다.
- 벌크 갱신을 사용한다면 버전 조건과 버전 증가를 쿼리에 명시해야 한다.
- 버전 충돌과 현재 상태에서 허용되지 않는 전이는 서로 다른 실패로 구분한다.

## 13. 아직 결정하지 않은 항목

### 13.1 사용자 세부 규칙

- 사용자 등록·조회가 다루는 최소 속성과 중복 판단 기준

### 13.2 API 설계에서 결정할 항목

- 엔드포인트와 요청·응답 구조
- 검색 대상과 페이징 기본값
- 입력값 길이와 필수 여부
- 오류 응답 형식과 HTTP 상태 코드
- Swagger 확인용 초기 데이터

### 13.3 교차 동시성

- 담당자 지정과 해당 멤버 제거의 경쟁은 [트랜잭션 경계 설계 4.2절](./transaction-boundaries.md#42-담당자-지정과-멤버-제거의-경쟁)을 따른다.
- 멤버 제거로 여러 Task를 미할당 처리할 때의 리비전과 잠금 규칙은 [트랜잭션 경계 설계 4.3절](./transaction-boundaries.md#43-여러-task-정규화)을 따른다.

## 14. 현재 범위에서 제외한 항목
