# Task 사용자 시나리오

- 작성일: 2026-08-25
- 근거 문서: [프로젝트 협업 서비스 구현 과제 안내서](../%5B채용%5D%20프로젝트%20협업%20서비스%20구현%20과제%20안내서.md), [도메인 정책 결정 기록](../domain-policies.md), [Task 상태와 전이 규칙](../task-state-transitions.md)
- 범위: Task의 생성, 승인, 실행, 담당자 관리, 조회, 삭제, 접근 통제와 동시 수정

## 1. 문서 목적과 범위

이 문서는 프로젝트 멤버가 Task를 제안하고, 관리자가 이를 승인하며, 담당자가 실행을 마치는 과정을 사용자 관점에서 설명한다. 각 시나리오는 행위자, 사전 조건, 흐름, 결과, 실패 또는 거부 조건을 명시한다.

다음 항목은 이 문서에서 다루지 않는다.

- API 경로, HTTP 메서드, 요청·응답 형식과 오류 코드
- 실제 인증과 로그인
- 댓글, 알림, 승인·반려 이력, 변경 이력
- 휴지통, 복구, 소프트 삭제

요청자는 과제 안내서대로 API 파라미터로 전달된 식별자를 통해 이미 특정되어 있다고 가정한다. 이 문서에서 **관리자**는 해당 프로젝트의 OWNER 또는 ADMIN을 뜻한다. 생성자와 담당자는 서로 다른 속성이며, 생성자는 Task가 삭제될 때까지 바뀌지 않는다.

한 사용자가 관리자, 생성자, 담당자 자격을 동시에 가질 수 있다. 각 행위는 요청 시점에 가진 자격을 기준으로 판단한다. 예를 들어 관리자가 현재 담당자라면 담당자 자격으로 작업을 시작할 수 있고 관리자 자격으로 내용을 수정할 수 있다. 다만 생성자가 자신의 `PENDING` Task를 승인할 수 없다는 금지는 그 사용자가 나중에 관리자가 되어도 그대로 적용한다.

Task를 변경하는 시나리오에서는 사용자가 마지막으로 조회한 리비전을 함께 제시한다고 가정한다. 리비전이 현재 값과 다를 때의 공통 처리는 `TASK-20`에서 설명한다.

## 2. Task 생성과 승인

### TASK-01. MEMBER가 Task를 제안한다

- **행위자:** 현재 프로젝트의 MEMBER
- **사전 조건:**
  - 행위자가 대상 프로젝트의 현재 멤버다.
  - 제목과 설명이 입력 정책을 만족한다.
- **흐름:**
  1. MEMBER가 프로젝트에 새 Task를 등록한다.
  2. 시스템은 요청자를 생성자이자 최초 담당자로 기록한다.
  3. 시스템은 관리자의 승인을 기다리는 상태로 Task를 등록한다.
- **결과:**
  - 상태는 `PENDING`이다.
  - 생성자와 담당자는 요청한 MEMBER로 같다.
  - 반려 사유는 없다.
- **실패 또는 거부 조건:**
  - 프로젝트의 현재 멤버가 아니면 생성할 수 없다.
  - 생성 시 다른 사용자를 담당자로 정하거나 미할당으로 만들 수 없다.
  - 입력값이 정책을 만족하지 않으면 생성되지 않는다.

### TASK-02. 관리자가 Task를 바로 등록한다

- **행위자:** 현재 프로젝트의 OWNER 또는 ADMIN
- **사전 조건:**
  - 행위자가 대상 프로젝트의 현재 관리자다.
  - 제목과 설명이 입력 정책을 만족한다.
- **흐름:**
  1. 관리자가 새 Task를 등록한다.
  2. 관리자는 자신을 기본 담당자로 유지하거나, 다른 현재 프로젝트 멤버를 담당자로 선택하거나, 담당자를 비워 둔다.
  3. 시스템은 별도의 승인 단계 없이 Task를 승인된 상태로 등록한다.
- **결과:**
  - 상태는 `ACCEPTED`이다.
  - 생성자는 요청한 관리자로 고정된다.
  - 담당자는 요청에 따라 생성자, 다른 현재 멤버 또는 미할당이다.
  - 반려 사유는 없다.
- **실패 또는 거부 조건:**
  - 선택한 담당자가 현재 프로젝트 멤버가 아니면 생성할 수 없다.
  - 행위자가 현재 관리자가 아니면 이 방식으로 생성할 수 없다.
  - 입력값이 정책을 만족하지 않으면 생성되지 않는다.

### TASK-03. 관리자가 PENDING Task를 승인한다

- **행위자:** Task 생성자가 아닌 현재 프로젝트의 OWNER 또는 ADMIN
- **사전 조건:**
  - Task가 `PENDING` 상태다.
  - 행위자가 현재 프로젝트 관리자다.
  - 행위자가 조회한 리비전이 현재 Task 리비전과 같다.
- **흐름:**
  1. 관리자가 Task의 내용을 확인한다.
  2. 관리자는 기존 담당자를 유지하거나, 다른 현재 멤버에게 재할당하거나, 담당자를 비우는 선택을 한다.
  3. 관리자가 Task를 승인한다.
- **결과:**
  - 상태는 `ACCEPTED`가 된다.
  - 별도 선택이 없으면 기존 담당자를 유지한다.
  - 승인 후 생성자는 생성자라는 이유만으로 제목과 설명을 수정할 수 없다.
  - 승인 후 현재 담당자는 제목과 설명을 수정할 수 있지만, 수정 결과는 다시 승인 대기로 돌아간다.
  - 반려 사유는 없는 상태를 유지한다.
- **실패 또는 거부 조건:**
  - 생성자는 자신이 만든 Task를 직접 승인할 수 없다.
  - 관리자가 아니면 승인할 수 없다.
  - `PENDING`이 아닌 Task에는 승인 행위를 적용할 수 없다.
  - 새 담당자로 현재 프로젝트 멤버가 아닌 사용자를 지정할 수 없다.
  - 리비전이 다르면 `TASK-20`에 따라 변경이 거부된다.

### TASK-04. 관리자가 PENDING Task를 반려한다

- **행위자:** 현재 프로젝트의 OWNER 또는 ADMIN
- **사전 조건:**
  - Task가 `PENDING` 상태다.
  - 행위자가 현재 프로젝트 관리자다.
  - 짧은 반려 사유가 준비되어 있다.
  - 행위자가 조회한 리비전이 현재 Task 리비전과 같다.
- **흐름:**
  1. 관리자가 Task의 내용을 확인한다.
  2. 관리자가 반려 사유를 남기고 Task를 반려한다.
- **결과:**
  - 상태는 `REJECTED`가 된다.
  - 최신 반려 사유 하나를 저장한다.
  - 생성자와 담당자는 그대로 유지한다.
  - Task는 삭제되지 않으며 프로젝트 멤버의 조회 결과에 계속 포함된다.
- **실패 또는 거부 조건:**
  - 관리자가 아니면 반려할 수 없다.
  - `PENDING`이 아닌 Task에는 반려 행위를 적용할 수 없다.
  - 반려 사유가 없거나 입력 정책을 만족하지 않으면 반려할 수 없다.
  - 리비전이 다르면 `TASK-20`에 따라 변경이 거부된다.

### TASK-05. 생성자가 승인 전 Task 내용을 수정한다

- **행위자:** Task 생성자
- **사전 조건:**
  - 생성자가 현재 프로젝트 멤버다.
  - Task 상태가 `PENDING` 또는 `REJECTED`다.
  - 행위자가 조회한 리비전이 현재 Task 리비전과 같다.
- **흐름:**
  1. 생성자가 제목 또는 설명을 수정한다.
  2. 시스템은 상태와 담당자를 바꾸지 않고 수정 내용을 반영한다.
- **결과:**
  - 제목 또는 설명이 변경된다.
  - 기존 상태는 그대로 유지된다.
  - `REJECTED` 상태라면 내용 수정만으로 재요청되지 않으며 기존 반려 사유도 유지된다.
- **실패 또는 거부 조건:**
  - 생성자가 아닌 일반 멤버는 수정할 수 없다.
  - 생성자가 더 이상 프로젝트 멤버가 아니면 수정할 수 없다.
  - `ACCEPTED`, `IN_PROGRESS`, `IN_REVIEW`, `DONE`에서는 생성자라는 이유만으로 제목과 설명을 수정할 수 없다.
  - 리비전이 다르면 `TASK-20`에 따라 변경이 거부된다.

### TASK-06. 생성자가 반려된 Task를 다시 요청한다

- **행위자:** Task 생성자
- **사전 조건:**
  - Task가 `REJECTED` 상태다.
  - 생성자가 현재 프로젝트 멤버다.
  - 행위자가 조회한 리비전이 현재 Task 리비전과 같다.
- **흐름:**
  1. 생성자는 필요하면 `TASK-05`에 따라 제목이나 설명을 먼저 수정한다.
  2. 생성자가 관리자에게 Task를 다시 검토해 달라고 요청한다.
- **결과:**
  - 상태는 `PENDING`이 된다.
  - 기존 반려 사유를 비운다.
  - 생성자와 담당자는 바뀌지 않는다.
- **실패 또는 거부 조건:**
  - 생성자가 아닌 사용자는 재요청할 수 없다.
  - 생성자가 프로젝트에서 제거된 경우에는 재요청할 수 없다.
  - `REJECTED`가 아닌 Task에는 재요청을 적용할 수 없다.
  - 제목이나 설명을 수정하는 행위만으로 재요청된 것으로 처리하지 않는다.
  - 리비전이 다르면 `TASK-20`에 따라 변경이 거부된다.

### TASK-07. 관리자가 Task 내용을 수정한다

- **행위자:** 현재 프로젝트의 OWNER 또는 ADMIN
- **사전 조건:**
  - 행위자가 현재 프로젝트 관리자다.
  - 행위자가 조회한 리비전이 현재 Task 리비전과 같다.
- **흐름:**
  1. 관리자가 Task의 제목 또는 설명을 수정한다.
  2. 시스템은 현재 상태를 바꾸지 않고 수정 내용을 반영한다.
- **결과:**
  - 관리자는 모든 상태에서 제목과 설명을 수정할 수 있다.
  - 관리자가 동시에 Task 생성자 또는 담당자여도 관리자 자격으로 수정할 수 있다.
  - `ACCEPTED` 이후의 수정은 관리자가 승인한 내용 변경으로 간주하며 기존 실행 상태를 유지한다.
  - `REJECTED` 상태의 수정은 자동 재요청으로 처리하지 않는다.
- **실패 또는 거부 조건:**
  - 현재 프로젝트 관리자가 아니면 이 권한으로 수정할 수 없다.
  - 제목이나 설명이 입력 정책을 만족하지 않으면 수정되지 않는다.
  - 리비전이 다르면 `TASK-20`에 따라 변경이 거부된다.

### TASK-07A. 담당자가 승인된 Task 내용을 수정해 다시 승인받는다

- **행위자:** Task의 현재 담당자
- **사전 조건:**
  - Task가 `ACCEPTED`, `IN_PROGRESS`, `IN_REVIEW`, `DONE` 중 하나다.
  - 행위자가 현재 프로젝트 멤버이자 현재 담당자다.
  - 행위자가 조회한 리비전이 현재 Task 리비전과 같다.
- **흐름:**
  1. 현재 담당자가 제목 또는 설명을 수정한다.
  2. 시스템은 담당자 자격과 현재 상태를 확인한다.
  3. 시스템은 수정 내용을 반영하고, 기존 승인과 실행 상태를 무효화한다.
- **결과:**
  - 상태는 `PENDING`이 된다.
  - 담당자는 유지된다.
  - 반려 사유는 비운다.
  - 따라서 이 `PENDING` Task는 생성자와 담당자가 다를 수 있다.
- **실패 또는 거부 조건:**
  - 현재 담당자가 아니면 이 흐름으로 수정할 수 없다.
  - 현재 담당자가 아닌 생성자는 승인된 Task를 수정할 수 없다.
  - 제목이나 설명이 입력 정책을 만족하지 않으면 수정되지 않는다.
  - 리비전이 다르면 `TASK-20`에 따라 변경이 거부된다.

## 3. 담당자 관리

### TASK-08. 관리자가 담당자를 지정하거나 바꾼다

- **행위자:** 현재 프로젝트의 OWNER 또는 ADMIN
- **사전 조건:**
  - Task가 `ACCEPTED`, `IN_PROGRESS`, `IN_REVIEW`, `DONE` 중 하나다.
  - 새 담당자가 대상 프로젝트의 현재 멤버다.
  - 행위자가 조회한 리비전이 현재 Task 리비전과 같다.
- **흐름:**
  1. 관리자가 미할당 Task에 담당자를 지정하거나 기존 담당자를 다른 멤버로 교체한다.
  2. 시스템은 새 담당자를 기록한다.
- **결과:**
  - 담당자가 새로 선택한 현재 프로젝트 멤버로 바뀐다.
  - 직접 재할당한 경우 기존 상태는 그대로 유지된다.
  - `ACCEPTED` Task에 담당자를 지정해도 자동으로 `IN_PROGRESS`가 되지 않는다.
- **실패 또는 거부 조건:**
  - 관리자가 아니면 다른 사용자를 담당자로 지정할 수 없다.
  - 새 담당자가 현재 프로젝트 멤버가 아니면 지정할 수 없다.
  - `PENDING`의 담당자 변경은 승인과 함께할 때만 가능하다.
  - `REJECTED`에서는 담당자를 지정하거나 바꿀 수 없다.
  - 리비전이 다르면 `TASK-20`에 따라 변경이 거부된다.

### TASK-09. 관리자가 담당자를 해제한다

- **행위자:** 현재 프로젝트의 OWNER 또는 ADMIN
- **사전 조건:**
  - Task가 `ACCEPTED`, `IN_PROGRESS`, `IN_REVIEW`, `DONE` 중 하나다.
  - Task에 현재 담당자가 있다.
  - 행위자가 조회한 리비전이 현재 Task 리비전과 같다.
- **흐름:**
  1. 관리자가 현재 담당자를 해제한다.
  2. 시스템은 담당자를 비우고 상태 정규화 규칙을 함께 적용한다.
- **결과:**

  | 기존 상태 | 해제 후 상태 | 담당자 |
  | --- | --- | --- |
  | `ACCEPTED` | `ACCEPTED` | 없음 |
  | `IN_PROGRESS` | `ACCEPTED` | 없음 |
  | `IN_REVIEW` | `ACCEPTED` | 없음 |
  | `DONE` | `DONE` | 없음 |

- **실패 또는 거부 조건:**
  - 관리자가 아니면 다른 사용자의 담당을 해제할 수 없다.
  - `PENDING`, `REJECTED`의 담당자는 이 행위로 해제할 수 없다.
  - 리비전이 다르면 `TASK-20`에 따라 변경이 거부된다.

### TASK-10. 담당자가 자신의 담당을 포기한다

- **행위자:** Task의 현재 담당자

검색 대상 필드, 기본 페이지 크기와 정렬 기준은 이 사용자 시나리오에서 확정하지 않는다.

### TASK-17. 권한이 있는 사용자가 Task를 삭제한다

- **행위자:** 현재 프로젝트의 OWNER·ADMIN 또는 상태에 따라 삭제 권한이 있는 현재 담당자

  - 행위자가 조회한 리비전이 현재 Task 리비전과 같다.
- **흐름:**
  1. 권한이 있는 사용자가 Task 삭제를 요청한다.
  2. 시스템은 현재 상태와 행위자의 역할 및 담당자 여부를 확인한다.
  3. 시스템은 Task를 완전히 삭제한다.
- **결과:**

  | 현재 상태 | 삭제 가능한 사람 | 삭제 의미 |
  | --- | --- | --- |
  | `PENDING` | 현재 담당자인 생성자, OWNER, ADMIN | 승인 전 제안 철회 또는 관리자 삭제 |

  - `ACCEPTED` 이후의 일반 담당자는 담당자라는 이유만으로 Task를 삭제할 수 없다.
  - 현재 담당자가 OWNER 또는 ADMIN도 겸한다면 관리자 자격으로는 `ACCEPTED` 이후 Task를 삭제할 수 있다.
  - `PENDING` 또는 `REJECTED`의 생성자가 프로젝트에서 제거되어 담당자가 비어 있으면 관리자만 삭제할 수 있다.
  - 현재 프로젝트 멤버가 아니면 삭제할 수 없다.
  - 리비전이 다르면 `TASK-20`에 따라 삭제가 거부된다.

## 6. 접근 통제와 동시성

### TASK-18. 허용되지 않은 상태 전이를 거부한다

- **행위자:** Task 변경을 요청하는 프로젝트 멤버
- **사전 조건:**
  - 행위자가 현재 프로젝트 멤버지만, 요청한 전이가 현재 상태 또는 자신의 자격에 허용되지 않는다.
- **흐름:**
  1. 프로젝트 멤버가 Task의 상태 변경을 요청한다.
  2. 시스템은 현재 상태, 필요한 시작 상태, 행위자의 역할 또는 담당자 여부를 확인한다.
  3. 정의되지 않은 전이를 적용하지 않는다.
- **결과:**
  - Task의 상태, 담당자, 내용과 리비전은 바뀌지 않는다.
  - 담당자 해제에 따른 `IN_PROGRESS·IN_REVIEW → ACCEPTED` 정규화만 일반 상태 전이의 예외로 취급한다.
- **실패 또는 거부 조건:**
  - `PENDING → IN_PROGRESS·DONE`
  - `REJECTED → ACCEPTED·IN_PROGRESS`
  - `ACCEPTED → IN_REVIEW·DONE`
  - 담당자 해제 사유가 없는 `IN_PROGRESS·IN_REVIEW → ACCEPTED`
  - `IN_PROGRESS → DONE`
  - `DONE → ACCEPTED·IN_PROGRESS`
  - 이미 반영되어 시작 상태가 달라진 동일 명령의 반복 호출

### TASK-19. 프로젝트 외부 사용자의 모든 Task 접근을 막는다

- **행위자:** 대상 프로젝트에 속하지 않은 사용자
- **사전 조건:**
  - 행위자가 서비스 사용자로 식별되었지만 대상 프로젝트의 현재 멤버가 아니다.
- **흐름:**
  1. 외부 사용자가 대상 프로젝트의 Task 생성, 상세 조회, 목록·검색, 수정, 상태 전환, 담당자 변경 또는 삭제 중 하나를 요청한다.
  2. 시스템은 대상 프로젝트의 현재 멤버십을 확인한다.
  3. 시스템은 요청을 수행하지 않는다.
- **결과:**
  - Task 데이터는 조회 결과에 노출되지 않는다.
  - Task의 내용, 상태, 담당자와 리비전은 변경되지 않는다.
  - 다른 프로젝트의 목록이나 검색 결과에도 대상 Task가 섞이지 않는다.
- **실패 또는 거부 조건:**
  - 과거에 멤버였더라도 현재 제거된 사용자는 접근할 수 없다.
  - 다른 프로젝트에서 OWNER 또는 ADMIN이더라도 대상 프로젝트의 멤버가 아니면 접근할 수 없다.
  - Task의 담당자나 생성자로 기록되어 있더라도 현재 멤버가 아니면 접근할 수 없다.

### TASK-20. 동시에 변경된 Task에 오래된 리비전으로 요청한다

- **행위자:** 같은 Task를 변경하려는 권한 있는 프로젝트 멤버 둘 이상
- **사전 조건:**
  - 두 사용자가 같은 Task의 동일한 리비전을 조회했다.
  - 각 사용자는 자신이 요청할 행위에 필요한 권한을 가지고 있다.
- **흐름:**
  1. 두 사용자가 리비전 `N`인 같은 Task를 조회한다.
  2. 첫 번째 사용자가 리비전 `N`을 기준으로 유효한 변경을 요청한다.
  3. 시스템은 첫 번째 변경을 반영하고 Task 리비전을 증가시킨다.
  4. 두 번째 사용자가 이전 리비전 `N`을 기준으로 다른 변경을 요청한다.
  5. 시스템은 현재 리비전과 요청 리비전이 다름을 확인하고 두 번째 변경을 거부한다.
  6. 두 번째 사용자는 최신 Task를 다시 조회한 뒤 변경 여부를 판단한다.
- **결과:**
  - 먼저 반영된 변경은 유지된다.
  - 나중 요청이 먼저 반영된 내용을 덮어쓰거나 자동 병합하지 않는다.
  - 거부된 요청으로 Task의 상태, 내용, 담당자와 현재 리비전은 바뀌지 않는다.
- **실패 또는 거부 조건:**
  - 승인과 반려, 내용 수정, 실행 상태 전환, 담당자 지정·변경·해제, 담당 포기와 삭제 모두 같은 리비전 검사를 통과해야 한다.
  - 두 관리자가 각각 승인과 반려를 요청하거나 완료 승인과 보완 요청을 하더라도 먼저 유효하게 반영된 하나만 성공한다.
  - 생성자의 내용 수정과 관리자의 승인·반려가 겹치거나 담당자 변경과 상태 전환이 겹쳐도 먼저 반영된 하나만 성공한다.
  - 담당자의 승인된 Task 내용 수정과 관리자의 완료 승인 또는 보완 요청이 겹쳐도 먼저 반영된 하나만 성공한다.
  - 리비전은 같지만 현재 상태에서 허용되지 않는 전이라면 동시성 충돌이 아니라 `TASK-18`의 잘못된 상태 전이로 거부한다.

## 7. 프로젝트 멤버 제거와 Task 정규화

### TASK-21. 담당자인 프로젝트 멤버를 제거한다

- **행위자:** 멤버 제거 권한이 있는 OWNER·ADMIN 또는 탈퇴하는 MEMBER·ADMIN 본인
- **사전 조건:**
  - 프로젝트 멤버 제거 또는 탈퇴 요청 자체가 프로젝트 정책에 따라 허용된다.
  - 제거되는 사용자가 하나 이상의 Task 담당자다.
- **흐름:**
  1. 권한이 있는 사용자가 프로젝트 멤버를 제거하거나 본인이 탈퇴한다.
  2. 시스템은 해당 사용자의 프로젝트 멤버십을 제거한다.
  3. 시스템은 제거된 사용자가 담당하던 모든 Task의 담당자를 비운다.
  4. 각 Task의 기존 상태에 따라 상태 정규화를 함께 적용한다.
- **결과:**

  | 기존 상태 | 멤버 제거 후 상태 | 담당자 |
  | --- | --- | --- |
  | `PENDING` | `PENDING` | 없음 |
  | `REJECTED` | `REJECTED` | 없음 |
  | `ACCEPTED` | `ACCEPTED` | 없음 |
  | `IN_PROGRESS` | `ACCEPTED` | 없음 |
  | `IN_REVIEW` | `ACCEPTED` | 없음 |
  | `DONE` | `DONE` | 없음 |

  - 제거된 사용자가 Task 생성자여도 생성자 정보는 유지한다.
  - `IN_PROGRESS`와 `IN_REVIEW` Task는 담당자 없는 활성 상태로 남지 않는다.
  - 멤버 제거 결과에 미할당으로 변경된 Task 수를 별도로 포함하지 않는다.
- **실패 또는 거부 조건:**
  - 멤버 제거 또는 탈퇴 자체가 프로젝트 권한 규칙에 어긋나면 멤버십과 Task를 모두 변경하지 않는다.
  - OWNER는 이 흐름으로 탈퇴할 수 없으며, 먼저 다른 ADMIN에게 소유권을 이전해야 한다.
  - 제거된 생성자는 더 이상 자신의 `PENDING`·`REJECTED` Task를 수정하거나 삭제하거나 재요청할 수 없다.
  - `REJECTED` Task의 생성자가 제거된 경우, 현재 정책에서는 관리자가 내용을 수정하거나 삭제할 수 있지만 대신 재요청할 수는 없다.

담당자 지정과 멤버 제거가 동시에 일어나는 경우, 여러 Task를 한꺼번에 정규화할 때의 리비전 처리 방식은 [트랜잭션 경계 설계 4.2절과 4.3절](../transaction-boundaries.md#42-담당자-지정과-멤버-제거의-경쟁)을 따른다.

## 8. 대표 사용자 여정

### 일반 MEMBER가 제안한 Task를 완료한다

~~~text
TASK-01 MEMBER 생성
→ PENDING, 생성자=담당자
→ TASK-03 관리자 승인
→ ACCEPTED
→ TASK-11 담당자 시작
→ IN_PROGRESS
→ TASK-12 담당자 완료 검토 요청
→ IN_REVIEW
→ TASK-13 관리자 완료 승인
→ DONE
~~~

### 반려된 제안을 고쳐 다시 요청한다

~~~text
TASK-01 MEMBER 생성
→ PENDING
→ TASK-04 관리자 반려
→ REJECTED, 최신 반려 사유 저장
→ TASK-05 생성자 내용 수정
→ REJECTED 유지
→ TASK-06 생성자 재요청
→ PENDING, 반려 사유 제거
→ TASK-03 관리자 승인
→ ACCEPTED
~~~

### 승인된 작업의 담당자가 내용을 바꾸고 다시 승인받는다

~~~text
관리자가 Task 생성 또는 기존 Task 승인
→ ACCEPTED 또는 그 이후 상태
→ TASK-07A 현재 담당자 내용 수정
→ PENDING, 담당자 유지
→ TASK-03 관리자 재승인
→ ACCEPTED
~~~

### 진행 중인 담당자가 포기하고 새 담당자가 이어받는다

~~~text
IN_PROGRESS
→ TASK-10 현재 담당자 포기
→ ACCEPTED, 미할당
→ TASK-08 관리자 새 담당자 지정
→ ACCEPTED
→ TASK-11 새 담당자 시작
→ IN_PROGRESS
~~~
