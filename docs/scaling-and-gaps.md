# 회사별 데이터 분리와 미완성 항목

## 회사별 데이터 분리

### 기본 선택: 공유 데이터베이스와 행 단위 분리

불특정 다수가 가입하는 SaaS 또는 여러 고객사가 함께 쓰는 일반적인 형태라면 공유 데이터베이스와 공유 스키마를 유지하고 `Company`를 추가한다. User와 Company의 관계가 필요하면 `CompanyMember`를 두고, Project에 `companyId`를 저장한다. Task는 Project 소속으로 회사를 판별하되 조회 비용과 격리 검증 단순화를 위해 `companyId`를 중복 저장하는 선택도 가능하다.

- 인증 결과에서 `companyId`와 `userId`를 얻어 요청 컨텍스트로 전달한다.
- 모든 저장소 조회와 변경 조건에 `companyId`를 강제한다. 식별자 단독 조회 메서드는 허용하지 않는다.
- 유일성 제약과 인덱스의 범위를 회사 단위로 바꾼다. 예: `(company_id, email)`, `(company_id, project_id)`.
- 멤버 추가 시 사용자와 프로젝트가 같은 회사인지 애플리케이션에서 검증한다.
- 캐시 키, 파일 경로, 메시지 이벤트, 감사 로그에도 `companyId`를 포함한다.
- 다른 회사 자료가 섞이지 않는 저장소 및 HTTP 통합 테스트를 둔다.

현재 프로젝트의 원칙대로 물리 외래 키는 추가하지 않고 애플리케이션이 참조 무결성을 관리한다.

### 예외 선택: 회사별 스키마 또는 데이터베이스

고객 수가 적더라도 고객이 직접 데이터베이스에 접근해야 하거나 계약·감사·보안 조건으로 물리 분리를 요구하면 스키마 또는 데이터베이스를 분리한다. 이는 기술 취향보다 상품 계약과 운영 모델의 결정이다.

물리 분리를 택하면 테넌트별 연결 라우팅, 스키마 마이그레이션, 백업·복구, 모니터링, 장애 대응을 별도로 운영해야 한다. 격리는 강해지지만 고객 수에 비례해 운영 비용과 배포 복잡도가 증가한다.

## 구현하지 못했거나 의도적으로 제외한 부분

- 담당자 재할당과 같은 사용자의 프로젝트 멤버 제거가 동시에 실행되는 교차 충돌은 완전히 해결하지 못했다. 하나의 일관성 경계나 멤버십 리비전을 명령에 포함하는 방식을 검토한다.
- 화면과 사용자 여정을 먼저 설계하지 않아 조회 API가 자원 단위 응답에 머물렀다. 실제 화면이 정해지면 목록 요약, 통계, 역할별 대시보드 같은 조회 전용 모델을 추가한다.
- 인증은 과제 범위에서 제외했다. 운영 환경에서는 `userId` 파라미터를 제거하고 인증 주체와 회사 컨텍스트에서 식별자를 가져온다.
- 프론트엔드는 과제 범위에 따라 구현하지 않았다. Swagger UI와 초기 데이터로 주요 흐름을 확인한다.
