# 설계 결정

이 문서는 구현에 반영된 판단의 정본이다.

## D-01. Task를 협업 티켓으로 해석

- 결정: Task를 Jira 이슈나 GitHub Issue와 같은 협업 티켓으로 해석하고 `PENDING → ACCEPTED/REJECTED → IN_PROGRESS → IN_REVIEW → DONE` 흐름을 설계했다.
- 근거: 과제에 `OWNER`, `ADMIN`이 있고 이들이 작업을 관리한다. 관리 책임을 단순 권한이 아니라 제안 승인과 완료 검토로 구체화했다.
- 비용/대안: 과제에 명시되지 않은 승인 흐름이 추가됐다. 단순 상태 CRUD보다 설명할 정책은 늘지만, 백엔드에서 상태와 권한을 어떻게 판단하는지 드러난다.

## D-02. 도메인 모델을 선택적으로 적용

- 결정: 시간에 따라 상태가 변하고 전이 규칙이 있는 Task만 행위 중심 도메인 모델로 만들었다. User와 Project의 단순 CRUD 및 권한 조합은 서비스 계층에서 전개한다.
- 근거: User와 Project에는 별도 모델을 정당화할 만큼 풍부한 행위를 도출할 근거가 부족했다. 모든 영역에 같은 모델링 방식을 적용하지 않았다.
- 비용/대안: 서비스 코드가 절차적으로 보이는 비용이 있다. 정책이 늘어나면 해당 영역도 도메인 모델로 이동할 수 있다.

## D-03. Task 도메인과 JPA 모델 분리

- 결정: 순수 Task 모델과 `TaskEntity`를 분리하고 매퍼와 저장소 어댑터를 둔다.
- 근거: JPA 엔티티 생명주기와 연관관계 규칙을 도메인 객체에 유입시키지 않기 위해서다. JPA는 저장, 식별자 조회, JPQL, `@Version`에 한정해 사용한다.
- 비용/대안: 명시적인 매핑 코드와 사람이 두 모델을 함께 인지해야 하는 비용을 감수한다. 관련 관점은 [JPA에 관한 간단한 글](https://blog.yullreas.com/posts/jpa-%EC%97%90-%EA%B4%80%ED%95%9C-%EA%B0%84%EB%8B%A8%ED%95%9C-%EA%B8%80)에 정리돼 있다.
- 관련 코드: `task/domain/Task.java`, `task/persistence/TaskEntity.java`, `task/persistence/TaskMapper.java`

## D-04. ID 값 참조와 물리 외래 키 미사용

- 결정: JPA 연관관계 대신 식별자 값을 저장한다. Task의 생성자와 담당자는 `Creator`, `Assignee` 값 객체이며 물리 외래 키를 두지 않는다.
- 근거: 객체 그래프 탐색과 영속성 전파가 필요하지 않다. 참조 행 쓰기와 대상 행 변경·삭제 사이의 잠금 및 실행 순서 결합도 애플리케이션 경계로 드러내고 싶었다.
- 비용/대안: 데이터베이스가 참조 무결성을 보장하지 않는다. 서비스가 존재 확인, 멤버십 확인, 삭제 순서와 담당자 정규화를 책임한다.

## D-05. 클라이언트 리비전과 낙관적 잠금 병용

- 결정: Task 변경 요청은 조회 응답의 `revision`을 다시 보내며, 엔티티에는 JPA `@Version`을 적용한다. 멤버십 변경은 Project 버전을 갱신해 마지막 OWNER 규칙을 보호한다.
- 근거: 상태 분기 충돌뿐 아니라 관리자가 읽은 내용이 바뀐 뒤 승인하는 충돌을 막아야 한다. 요청 리비전은 오래된 화면을, `@Version`은 실제로 겹친 트랜잭션을 감지한다.
- 대안: 조건부 `UPDATE`만으로 상태 분기는 처리하지만 승인 대상 내용의 동일성은 표현하지 못한다. 비관적 잠금은 사용자가 화면을 읽고 고민하는 요청 간 시간을 보호하지 못하면서 직렬화 범위만 늘린다.
- 한계: 담당자 재할당과 같은 사용자의 멤버 제거가 동시에 실행되는 교차 충돌은 완전히 닫지 못했다.

## D-06. 상태 전이는 명령형 하위 경로로 표현

- 결정: `approve`, `reject`, `start`, `request-review`, `complete`처럼 전이별 엔드포인트를 사용한다.
- 근거: API 초안은 AI 에이전트에 위임했다. 검토 결과, 현재처럼 허용 주체·선행 상태·부수 효과가 다른 전이는 범용 상태 수정 API보다 의도를 명시하고 요청 형식과 권한을 분리하기 쉽다고 판단해 유지했다.
- 비용/대안: 전이가 늘면 엔드포인트 수도 늘어난다. 전이 종류가 동적이거나 단순해지면 단일 transition 명령이나 일반 수정 API가 대안이다.

## D-07. 경계 검증과 정책 검증을 분리

- 결정: 컨트롤러 요청 DTO는 Bean Validation으로 형식과 필수값을 검사한다. 서비스와 도메인은 호출 경로와 무관하게 역할, 상태, 멤버십, 불변식을 다시 검사한다.
- 근거: `@Valid`는 HTTP 입력 품질을 빠르게 거절하지만 도메인 규칙을 대신하지 못한다. 도메인 객체는 컨트롤러 외부에서도 유효해야 한다.
- 응답: 외부 오류 형식은 `ApiErrorResponse(code, message, violations)`로 통일하고 내부 예외는 도메인별로 유지한다.

## D-08. 인증 제외, 인가는 애플리케이션에서 수행

- 결정: 과제 조건대로 Spring Security와 인증을 넣지 않고 `userId`를 인증된 요청자의 식별자라고 가정한다. 인가는 서비스에서 역할과 리소스 관계를 함께 검사한다.
- 근거: 현재 정책은 `OWNER/ADMIN/MEMBER` 역할만으로 끝나지 않고 생성자와 담당자 관계도 필요하다. 따라서 순수 RBAC가 아니다.
- 운영 전 변경: 외부 입력 `userId`를 제거하고 인증 주체에서 사용자 식별자를 얻어야 한다.

## D-09. 조회는 정적 JPQL 사용

- 결정: Task 조회는 객체 그래프 탐색 대신 정적 JPQL과 DTO 변환을 사용한다.
- 근거: 검색 조건이 프로젝트, 검색어, 상태, 페이징으로 고정돼 있어 별도 쿼리 빌더의 생성 코드와 추상화 비용이 더 크다.
- 대안: 동적 조회가 복잡해져 쿼리 빌더가 필요해지면 jOOQ 같은 SQL 중심 도구가 검토 대상이다. 현재 범위에는 필요하지 않다.

## D-10. 읽기/쓰기 서비스 분리는 CQRS가 아님

- 결정: `TaskReadService`와 `TaskWriteService`를 책임, 트랜잭션 속성, 저장소 의존성, 파일 크기에 따라 분리했다.
- 근거: 읽기와 쓰기는 동일 데이터베이스와 영속성 모델을 사용한다. 별도 읽기 모델이나 동기화 경계가 없으므로 CQRS라고 부르지 않는다.

## D-11. 통합 테스트 우선

- 결정: JPA 매핑, 트랜잭션, HTTP 계약과 권한 흐름을 함께 확인하는 통합 테스트를 우선했다.
- 근거: 초기 개발 단계에서는 도메인 정책이 가장 자주 바뀌어 세밀한 단위 테스트가 구현 변경과 함께 대량 수정될 가능성이 높았다.
- 비용/대안: 실패 원인 격리가 느리고 테스트 실행 비용이 크다. 안정된 핵심 상태 전이와 불변식은 선택적으로 단위 테스트한다.

## D-12. 프로젝트 소유자와 완료 작업

- 결정: 프로젝트는 여러 OWNER를 허용하되 항상 한 명 이상 남아야 한다. 완료된 Task의 내용과 담당자는 변경할 수 없지만 OWNER·ADMIN의 삭제는 허용한다.
- 근거: 역할 변경 요구사항을 만족하면서 마지막 소유자 제거를 방지한다. 완료 기록은 변경 불가 상태로 보되, 관리자의 예외적 완전 삭제 권한은 유지한다.
